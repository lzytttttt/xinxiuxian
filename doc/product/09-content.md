# 09 · 内容方案

**解决"内容量不够，很快就见底"痛点。**

参考实现手写了 2000 条名称（还有 23 处跨档重复）+ 135 个事件，仍很快见底，因为：事件无冷却无记忆，且事件是 JS 闭包无法批量扩充。本篇给出可规模化的内容管线。

---

## 一、事件池规划

**目标 200 个事件，平均 2.4 个选项 → 约 480 个决策点。**

| 池 | 数量 | 稀有度 t1/t2/t3/t4 | 说明 |
|---|---|---|---|
| `mortal.early`（0-30 岁） | 45 | 60/30/7/3 | 铺垫、流派种子、首次羁绊 |
| `mortal.mid`（25-80 岁） | 55 | 45/35/15/5 | 宗门、炼丹、build 成型 |
| `mortal.late`（60-200 岁） | 40 | 30/35/25/10 | 渡劫准备、大乘、高光 |
| `immortal.lower`（101-150 级） | 35 | 25/35/28/12 | 仙界势力、混沌气、心魔 |
| `immortal.upper`（151-200 级） | 25 | 20/30/30/20 | 证道、道祖、宇宙级赌注 |
| **合计** | **200** | | |

### 子池（跨池分类）

| 子池 | 数量 | 归属 |
|---|---|---|
| 羁绊事件 | 35 | 分布在各境界段 |
| 宗门任务 | 30 | 独立 `Mission` 结构 |
| 链式事件 | 20 | 有前置 flag |
| 一次性事件 | 约 30 | `once: true` |

### 防重复设计

| 机制 | 参数 |
|---|---|
| `cooldownYears` | 8-15 年（同事件最短重现间隔） |
| `maxCount` | 1-3（本局最多触发次数） |
| `recencyQueue` | 最近 20 个事件 id，不重复抽取 |
| 文本变体 | 每个 outcome 写 3-4 个 `text` 变体 |

**一局 90 年约触发 30 个事件** → 玩家在约 6-8 局后才开始感到重复，约 15 局才饱和。

> 对比参考实现：`maxCount` 是唯一防重复机制，且 58 个事件用 `100` 作为"无限"哨兵值——等于没有限制。

## 二、写手工作流

### 文件组织

```
src/content/events/
├─ mortal/
│  ├─ early.ts        45 个
│  ├─ mid.ts          55 个
│  └─ late.ts         40 个
├─ immortal/
│  ├─ lower.ts        35 个
│  └─ upper.ts        25 个
├─ bond/              35 个羁绊事件
├─ sect/              30 个宗门任务
├─ alchemy/           丹药相关事件
├─ chain/             20 个链式事件
├─ tribulation/       天劫相关事件
└─ index.ts           汇总导出
```

每个文件导出 `satisfies EventDef[]` 数组。**写手只需往数组里加对象字面量**——不碰引擎、无注册步骤、无构建配置。

### 写手手册

`docs/event-authoring.md` 必须包含：
1. **三个完整示例**（2 选项 / 3 选项含资源门槛 / 链式事件）——见 [tech/02-effect-dsl.md](../tech/02-effect-dsl.md#五三个完整示例)
2. **全部 `Target` 字符串速查表**
3. **全部 `ZoneId` 与乘区说明**
4. **全部 `Condition` op 速查表**
5. **数值参考表**（各境界段的合理数值范围，避免写出"给 10 级玩家 +100 万修为"的事件）

**写手不应该需要读引擎代码。**

### 数值护栏

写手手册提供各境界段的数值参照：

| 境界段 | 合理修为收益 | 合理灵根/气运收益 | 合理模拟点收益 |
|---|---|---|---|
| 1-30 级 | 当前修为的 1%-5%，保底 10-100 | +1-3 | +1-3 |
| 31-60 | 2%-6%，保底 500-5000 | +2-5 | +2-5 |
| 61-90 | 3%-8%，保底 1万-10万 | +3-8 | +3-8 |
| 91-100 | 5%-10%，保底 10万-50万 | +5-12 | +5-12 |
| 仙界 | 5%-12%，保底 100万-1000万 | +8-20 | 转修为 |

**推荐用比例式效果**（`{ op:'pct', target:{k:'cultivation'}, value:5 }`）而非绝对值——自动随境界缩放。

## 三、名称组合生成

**不手写 1000 条名称。** 改为构建期从带标签的词池组合生成，产物提交到仓库。

### 词池结构

```ts
interface NamePool {
  tier: number;
  modifiers: { text: string; tags: string[]; weight: number }[];
  nouns: { text: string; class: NounClass; weight: number }[];
  compat: Record<string, NounClass[]>;        // 修饰语标签 → 允许的名词类
  suffixes?: { text: string; weight: number }[];
  blocklist: string[];
}

type NounClass = 'weapon'|'art'|'beast'|'ghost'|'demon'|'place'|'herb'|'pill'|'body';
```

### 生成量

每档 60 修饰 × 60 名词 = 3600 原始组合。`compat` 标签过滤（如「噬魂」只配 `beast|ghost|demon`，「青锋」只配 `weapon|art`）后约剩 **30-35% → 每档约 1150 条**。

| 表 | 词池 | 总量 |
|---|---|---|
| 机缘 | 60 修饰 × 60 名词，5 个名词类 | ~11,500 |
| 法宝 | 50 材质前缀 × 50 名词 × 12 后缀 | ~9,000 |
| 灵草 | 40 × 40 | ~6,000 |
| 功法 | 30 × 30，带流派标签 | ~3,500 |
| 丹方 | 25 × 25 | ~3,000 |
| NPC 名 | 120 姓 × (200 男名 + 180 女名) | ~45,000 |
| 洞府/地名 | 40 × 40 | ~8,000 |
| **合计** | **约 600 个手写 token** | **~85,000 条** |

**约 140:1 的杠杆比。** 对比参考实现手写 2000 条。

### 质量护栏

| 护栏 | 说明 |
|---|---|
| **跨档全表精确去重** | 参考实现有 23 处跨档重复，读起来就是重复 |
| **同字拒绝** | 修饰语与名词含相同字则拒绝（干掉「青锋剑剑」） |
| **字数区间** | 1-3 档 3-5 字，8-10 档 5-8 字——**名字越长越像高手，这是免费的强度暗示** |
| **blocklist 进仓库** | 生成器遇到被屏蔽组合**直接报错**，防止后续加屏蔽项时静默回归 |
| **确定性生成** | 产物 `src/content/generated/names.json` 提交到仓库，diff 可审、可 grep、可屏蔽 |

### 生成器

`tools/gen-names.ts`，用 `tsx` 运行：

```bash
npx tsx tools/gen-names.ts            # 生成
npx tsx tools/gen-names.ts --check    # 校验产物与词池一致（CI 用）
```

**产物提交而非运行时生成**：让写手能审查、能屏蔽、能让 diff 可读。

## 四、内容校验

`tools/validate-content.ts` 是 CI 关卡：

| 规则 | 级别 |
|---|---|
| 事件 id 唯一 | **error** |
| `target` 在 `targets.ts` 中存在 | **error** |
| `grant.id` 能在对应内容表中解析 | **error** |
| `show`/`enable` 引用的 flag 有事件写入 | **error**（被读但无人写） |
| 事件写入的 flag 有事件读取 | warning（被写但无人读） |
| 每个事件在 500 个采样状态下至少触发一次 | **error**（可达性） |
| `once: true` 与 `maxCount` 同时出现 | warning（冗余） |
| **禁止事件把 `realm` 当作字段** | **error** |
| 无 `when` 的兜底 outcome 必须在数组末尾 | **error** |
| 兄弟 `chance` 节点路径唯一 | **error** |

> **「禁止 `realm` 字段」这条修掉参考实现最隐蔽的内容 bug**：仙界事件漏标 `realm: 2` 就永不触发（`sim.js:492` 是硬池过滤），而作者不会收到任何报错。本作改为位面门控一律走 `when`，且校验器强制。

## 五、总量估算

| 类别 | 文件数 | 估算大小 |
|---|---|---|
| 200 个事件（含文本变体） | 5-9 | ~180 KB |
| 生成的名称表 | 1 JSON | ~400 KB |
| 功法/丹方/宗门/命格/成就/图鉴定义 | ~14 | ~90 KB |
| 引擎 + 系统 | ~25 | ~55 KB |
| UI | ~30 | ~45 KB |
| **合计源码** | | **~770 KB**（gzip ~180 KB） |

**对比参考实现：8000 行 UMD 里约 84 KB 文案。**

内容量约 **5 倍**，代码量约 **1/3**——因为效果 DSL 取代了 JS 闭包，名称组合生成取代了手写列表。

## 六、验收标准

| 项 | 断言 | 命令 |
|---|---|---|
| 事件数达标 | ≥ 200 个事件，平均 ≥ 2.4 个选项 | `tsx tools/validate-content.ts --stats` |
| 内容合法 | 0 error、0 孤儿 flag | `tsx tools/validate-content.ts` |
| 事件可达 | 500 采样状态下每个事件至少触发一次 | `tsx tools/validate-content.ts` |
| 名称去重 | 跨档零重复 | `npx tsx tools/gen-names.ts --check` |
| 无 `realm` 字段 | 校验器强制 | `tsx tools/validate-content.ts` |
| 决策密度 | 单局 25-60 个决策 | `tsx tools/sim.ts --pacing` |
