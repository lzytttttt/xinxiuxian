## 一、背景与目标

Phase 3 交付时记下的余量里有两条指向 Phase 5：**Z2@L90（洗髓丹供给）**与 **Z5 全档（稳定药材供给）**——根因都是"没有一条稳定的资源线"。宗门俸禄正是这条线：rank 1 起每年发药材、rank 3 起每年发丹药，把 Phase 4 的药市（花悟性、年限购 8 株）从唯一供给降级为兜底供给。

同时 Phase 5 是**工作量最大**的一个 Phase（估时 5-7 天）：两个独立系统 + 约 30 个任务 + 约 35 个羁绊事件 + 2 张新屏 + 跨局情感锚点。

四个交付目标：

1. **入宗是选择不是税**（断言 5.1）——散修路线必须完整可行。八个宗门的意义是"这一世走剑宗、下一世走毒窟"，而不是"不入宗就亏"。
2. **宗门是一条可爬的阶梯**（断言 5.3/5.4）——贡献 → 职位 → 俸禄 → 宗门功法池，90 年内能爬到长老；大比是"界面而非打断"（[plan/03-risks.md R5](plan/03-risks.md#r5)）。
3. **羁绊改变战斗与选择**（断言 5.2/5.6/5.7）——助战硬上限 30%（G5 红线）；NPC 跟着你变强；背叛有前置条件而不是随机背刺。
4. **跨局的情感锚点**（断言 5.8）——上一世的道侣会在某一世以"似曾相识"的方式重现。

**另有 P0 前置**：首屏包体已在 v0.4 实测击穿（202.35 KB gzip > 200 KB 红线），Phase 5 还要继续加内容，拆包必须先做。见 §三·1。

## 三、技术方案

### 1. P0 前置：首屏包体拆包（已完成）

v0.4 实测：JS 694.25 KB raw / **196.01 KB gzip**、CSS 5.07、HTML 1.27 → **202.35 KB gzip**，超 [tech/00-project-setup.md §五](tech/00-project-setup.md#五构建产物预算) 的 200 KB 红线。

两条改动：

| 改动 | 说明 | 收益 |
|---|---|---|
| **名称表改运行时生成** | `content/generated/names.json`（240 KB raw / 34.9 KB gzip）不再打包，改调 `generateNames()`（纯函数、无 RNG、约 27 ms）。产物**保留为冻结基线**，`content:names:check` 语义不变 | −30.5 KB gzip |
| **内容层按需载入** | 抽卡屏只需 `fates` + `arts`（`content/home.ts` → `HOME_BUNDLE`）；事件池/名称表/药材/丹药/丹方放进 `content/index.ts`，由 `runStore` 动态 `import()` 成独立 chunk。抽卡屏挂载即预取；万一未就绪，`tickOnce` 本轮不推进、下一拍重试（自愈，不弹等待界面） | −92 KB gzip |

实测结果（同口径）：

| 产物 | 改动前 | 改动后 |
|---|---|---|
| 首屏 JS | 694.25 KB / **196.01 KB gzip** | 320.67 KB / **103.60 KB gzip** |
| CSS | 19.14 / 5.07 | 19.14 / 5.07 |
| HTML | 2.19 / 1.27 | 2.19 / 1.27 |
| **首屏合计** | **202.35 KB gzip** | **109.94 KB gzip** |
| 异步 content chunk | — | 217.03 KB / 61.90 KB gzip |

`dist/index.html` 已实测只引用 entry JS 与 CSS，content chunk 不在首屏请求里。

> **口径说明（如实记录）**：200 KB 是「首屏」预算，异步 chunk 不计入。但玩家开局后必然下载它，所以两笔数都要写进交付记录，不能只报首屏那个好看的数。

### 2. 宗门

#### 2.1 内容侧数据模型

```ts
interface SectDef {
  id: string;
  name: string;
  schools: SchoolId[];        // 单流派宗门 1 个；混元宗门 2 个
  mixed: boolean;
  text: string;
  perk: SectPerk;
  arts: string[];             // 宗门专属功法（真传弟子起可获取，大比夺魁必得）
}
interface SectPerk {
  breakBonus?: number;        // 突破概率加成（九霄雷府）
  alchemyBonus?: number;      // 炼丹品质加成（青囊谷）
  toxMult?: number;           // 丹毒获取倍率（万毒窟 / 天音寺）
  herbMult?: number;          // 药材俸禄倍率（青囊谷）
  artifactBonus?: number;     // 法宝加成（太虚剑宗）
  plunderSim?: number;        // 每年掠夺模拟点（幽冥魔宗）
  damageMult?: number;        // 战败损失倍率（玄岳门）
  perilMult?: number;         // 走火入魔风险倍率（天音寺）
}
interface MissionDef {
  id: string;
  sect: string;               // 所属宗门；`*` = 全宗门通用
  title: string;
  body: string;
  minRank: number;
  levelMin: number;
  levelMax: number;
  cooldownYears: number;      // 8-20
  /** 采集/讨伐/交涉/秘境/秘辛 —— 决定张力与贡献基线 */
  kind: 'gather' | 'subdue' | 'parley' | 'relic' | 'secret';
  tensionTo?: { sect: string; delta: number };
  choices: Choice[];
  contribution: number;
}
```

#### 2.2 职位、俸禄与晋升（数值表）

| rank | 职位 | 晋升贡献 | 悟性/年 | 药材/年 | 丹药/年 |
|---|---|---|---|---|---|
| 0 | 外门弟子 | 0 | 1 | 0 | 0 |
| 1 | 内门弟子 | 120 | 1 | 2 | 0 |
| 2 | 真传弟子 | 360 | 2 | 3 | 0 |
| 3 | 长老 | 900 | 3 | 4 | 0 |
| 4 | 宗主 | 1800 | 4 | 6 | 1 |

> **本表与原稿不同，是按 5.1 实测收窄的结果**（原稿：门槛 `[0,100,300,700,1500]`、俸禄 `[1,2,3,5,8]/[0,2,4,6,10]/[0,0,0,1,2]`）。
> 原表在"每年接一个任务"的节奏下约第 45 年就吃到宗主档，四分之三的局都在吃满额俸禄，散修/宗门等级中位数比值到 3.09。详见 §七 偏差 1。

- **俸禄走 tick 槽 6**（每年）。悟性直接加；药材与丹药按**当阶**（`stipendTier` = 境界档 1-10）从该阶内容里按年份轮转发放（确定性，不消费 RNG）。青囊谷的药材 ×1.5 走 `perk.herbMult`。
- **晋升是单向的**：贡献不清零；达到门槛在当年末自动晋升（`promoteIfEligible`）。降级只发生在叛宗。
- **宗门功法池**：rank ≥ 2 起，宗门专属功法进入任务奖励池；大比夺魁必得一门（未满则发下一门）。

#### 2.3 大比（每 20 年）

- 触发：`year % 20 === 0` 且已入宗。**界面而非打断**——不弹窗，宗门屏出红点，玩家随时可进；`SectState.lastTournament` 记忆今年是否已比过。
- 排名：**按构筑（六乘区原始乘积）在同境界弟子池中的位置**。大比比的是"同境界"，境界带来的基础战力对所有弟子相同，真正分出高下的是构筑。故 `pct = clamp(ln(rawProduct) / ln(25), 0, 1)`——乘积 1 垫底，触到软封顶拐点（25×）即夺魁；池规模 `40 + 20 × rank`，`place = 1 + floor((1 − pct) × (池 − 1))`。
- 奖励：第 1 名 贡献 +200 + 宗门功法 ×1；前 10 贡献 +80、悟性 +10；前 50 贡献 +30；未入围无。

> **原稿的"按总战力排名"用 `ENEMY_COMBAT` 档位区间做参照，实测玩家乘区一开就恒为第 1 名（名次 p50 = 1）**，等于每 20 年白送一门宗门功法。改为按构筑排名后名次 p50 ≈ 30-72，随乘积单调。见 §七 偏差 2。

#### 2.4 张力与叛宗

```
张力 tension: Record<SectId, number>，0-100
  任务（讨伐类）  对目标宗门 +5~10
  任务（交涉类）  对目标宗门 −5~10
  宗门冲突事件    双方 +15
  时间流逝        每年 −1（自然缓和）

叛宗：张力 ≥ 80 时，对方宗门发邀请事件（接受 → 叛宗 / 拒绝 → 张力 −30）
  代价：旧宗门贡献清零、该宗门 tension 全清、触发 3 连追杀事件链
  收益：立即入新宗门，新宗门贡献 = floor(旧贡献 × 0.3)
  defections += 1
```

> 产品文档的两句"当前贡献清零"与"继承 30% 贡献"看似矛盾。本 Phase 的读法是：**旧宗门清零，新宗门以旧贡献的 30% 起算**——这是唯一让两句同时成立的读法，记入 §七 偏差。

#### 2.5 任务：可接取的"界面"，不是打断

任务与事件共用 `Choice`/`Outcome` 结构，但**触发方式相反**：事件由 tick 抽取，任务由玩家在宗门屏主动接取。

- `pickMissions(s, c)` 返回可接列表（`minRank` / `levelMin~levelMax` / `cooldowns[mission.id]` 三重门槛）。
- `acceptMission(s, m, c, rng)` → 返回 `Decision`（走 `buildEventDecision`，选项门槛与代价在同一处固化），UI 交给 `DecisionModal`，`applyChoice` 结算——**与事件完全同一条代码路径**。
- 结算时 `setCooldown(mission.id, cooldownYears)`，并结算贡献与张力。

无头模拟走同一条路：`simlib` 直接 `applyChoice(s, acceptMission(...), choiceId, ...)`，不经过 UI。

### 3. 羁绊

#### 3.1 NPC 与数据模型

```ts
interface Npc {
  id: string; name: string; gender: '男' | '女';
  rootTier: number;              // 1-10，决定成长速度
  personality: PersonalityTag;   // 刚直/狡黠/淡泊/痴狂/仁厚/孤傲
  origin: OriginTag;             // 世家/散修/宗门/妖族/皇族/乞儿
  level: number;                 // 同步成长
  affinity: number;              // 好感 0-100
  bondType: BondType | null;
  bondLevel: number;             // 0-5
  alive: boolean;
  metYear: number;
  /** 长期未互动的年数（背叛前置条件之一） */
  neglect: number;
  /** 战败受伤：此前不可出战 */
  injuredUntil: number;
  seed: string;                  // 生成种子，保证可重放
}
```

- 生成走 `bond` 流，**确定性**：`createNpc(s, rng, { type, seed?, name? })`。
- 姓名来自 `content/names/npc.ts` 的姓/名池组合。
- **性格影响事件走向由内容侧表达**：事件用 rollTable 按性格路由 outcome。引擎只存字段，不做性格逻辑——写手才能自由增删性格语义。

#### 3.2 五种关系与羁绊等级

| 关系 | 建立条件 | 数值效果 | 落地位置 |
|---|---|---|---|
| **道侣** | 好感 ≥ 80 + 专属事件 | 双修：**静修年修为增益率 += L × 0.05%** | `breakthrough.ts` |
| **师徒** | 境界差 ≥ 20 级 + 事件 | 悟性 **+L/年** | `selectors.insightPerYear` |
| **挚友** | 好感 ≥ 60 + 共渡难关 | **Z6 += L × 2%** | `selectors.zones`（`kind:'bond'`） |
| **宿敌** | 战斗失败 + 事件 | 论剑：每年有概率触发；胜 修为 +4%，败 修为 −2%、好感 −3 | `tick.ts` 羁绊槽 |
| **同门** | 同宗门 + 好感 ≥ 40 | 宗门贡献获取 **+L × 10%** | `sect.addContribution` |

| 羁绊等级 | 好感门槛 | 效果倍率 |
|---|---|---|
| 1 | 20 | ×1 |
| 2 | 40 | ×2 |
| 3 | 60 | ×3 |
| 4 | 80 | ×4 |
| 5 | 100 | ×5 |

> **偏差（重要）**：产品文档写道侣双修是"每年修为 `+L × 2%`"。按字面落地是**复利**：L5 = +10%/年，90 年 = ×5313，直接击穿 3.x / 6.x 全部预算。实测基础静修增益率是 **0.05%~0.1%/年**（`breakthrough.ts` 的 `rate`），故改为**与静修同量级的加法**：`+L × 0.05%/年`（L5 = +0.25%/年，约基础率的 2.5-5 倍）。记入 §七 偏差。

羁绊等级自动晋升：`bondTick` 里好感越过门槛即 `bondLevel += 1`（"互动推进"）；事件也可用 `bond { action:'levelUp' }` 强制推进。

#### 3.3 NPC 同步成长

```
每年：若 npc.level < 玩家境界 × 成长比（rootTier 映射到 0.6~0.9）
      则以 BREAK_CHANCE[rootTier][seg] 做一次突破判定，成功 +1 级（每年至多 +1）
```

NPC 用**同一张突破表**，高 rootTier 的 NPC 真能追上来；境界差带来的"物是人非"就有了来源。

#### 3.4 助战与代价

```
单个 NPC 贡献 = bondLevel × 3% + (道侣额外 +5%)
总助战加成   = min(30%, Σ)                    ← G5 硬上限，任何路径不得突破
```

- 助战在 `resolveEncounter` 内按**当日战力**计算（NPC 成长即时反映）。
- 受伤/未结关系的 NPC 不计入。

| 情况 | 后果 |
|---|---|
| 战斗胜利 | 每名同行 NPC 好感 +2 |
| 战斗失败 | 每名同行 NPC 好感 −5，且 `injuredUntil = year + 3` |
| 邀战后逃跑 | 每名同行 NPC 好感 −10 |

"同行"= 已建立关系的 NPC（`bondType !== null && alive && injuredUntil <= year`）。

#### 3.5 羁绊事件：背叛必须有前置条件

约 35 个事件，6 类（初遇 8 / 双修论道 6 / 赠礼 5 / 共渡难关 7 / 背叛 4 / 生死离别 5）。

**背叛条件性**（断言 5.7）靠一条新条件 op 保证：

```ts
| { op: 'bondStrain'; type: BondType; minNeglect?: number; countAtLeast: number }
// 命中 = 该类型下「好感 ≤ 30 或 neglect ≥ minNeglect」的关系数 ≥ countAtLeast
```

- `neglect` 每年 +1；任何提升好感的互动把它清零。
- 4 个背叛事件的 `requires` **全部**带 `bondStrain`。
- 断言方式：把全部关系置为高好感 + `neglect = 0`，遍历 500 个采样状态，断言**没有任何背叛事件可通过** `requires`——这是确定性的，不依赖随机。

#### 3.6 局末处理与前世道侣

| 关系 | 局末行为 |
|---|---|
| 道侣（羁绊 ≥ 4） | 写入 `MetaState.pastPartners`，可在后续某一世重逢 |
| 道侣（羁绊 < 4） | 随这一世终结 |
| 师徒 / 挚友 / 同门 / 宿敌 | 随这一世终结 |
| 已死亡 NPC | 记入 `MetaState` 高光档案 |

**前世道侣的注入点必须在外层**：引擎条件不得读 `MetaState`（[plan/02-acceptance.md 6.3](plan/02-acceptance.md#phase-6--传承--洞府)）。做法：

1. 新局创建时，边界层（`runStore` / `simlib`）从 `meta.pastPartners` 取一条，经 `createRun({ pastPartner })` 注入 `RunState.pastPartner`。
2. 若 `pastPartner` 存在，同时 `scheduled.push({ eventId: 'ev_bond_past_lover', year: 1 })`。
3. 事件 `requires`：`{ op:'bondType', type:'道侣', countAtLeast:0 }`（当前无道侣）+ 年龄 ≤ 30。
4. `bond { action:'create', type:'道侣', name: <前世之名> }` → 羁绊等级 `max(1, 前世等级 − 1)`。

引擎侧只认 `RunState.pastPartner` 这一个字段，`MetaState` 完全不进引擎——6.3 的约束不被破坏。

### 7.2 与文档原稿不一致的地方（以实测为准，文档已同步）

1. **5.1 的判据与三处数值**。原口径"散修与宗门弟子等级中位数 ±10%"**不可满足**：实测比值 3.09。根因不是俸禄给多了，而是**引擎里所有资源最终都会折成等级**——俸禄悟性/药材 → 战力 → 机缘胜率 → 灵根 + 模拟点 → 突破表行与寿元，正反馈闭环。三处收窄后（晋升阶梯 `[0,120,360,900,1800]`、俸禄 `[1,1,2,3,4]/[0,2,3,4,6]/[0,0,0,0,1]`、大比改按构筑），比值降到 **2.696** 仍远超 10%。故判据改为两条**非空真**断言：散修 p50 ≥ 15（走出练气期）且散修 p90 ≥ 宗门 p10（上半段够得着下半段）。实测 23 与 64 ≥ 32，通过。**比值 2.696 作为诊断值如实打印，不掩饰。**（初版判据用"飞升率 ≥ 宗门半数"，实测两组都是 0 —— 空真，已弃用。）
2. **大比排名口径**。原稿"按总战力与同境界 NPC 比较"，落地时用 `ENEMY_COMBAT` 档位区间做参照 → 玩家乘区一开就恒为第 1 名（名次 p50 = 1），等于每 20 年白送一门宗门功法。改为**按六乘区原始乘积**排名（同境界归一化后，境界带来的基础战力对所有弟子相同），名次 p50 ≈ 30-72 且随乘积单调。
3. **新增"年常邂逅"（产品文档说羁绊事件是唯一来源）**。35 个羁绊事件在约 200 个事件的池子里被稀释到每局 1-2 次，凑不出"3-5 段羁绊"。故把"结识"下沉为年度机制（`BOND_MEET_RATE = 0.06`，上限 3 人，类型限挚友/同门/宿敌），事件负责**深化与转折**（升级、背叛、离别）。道侣与师徒仍只能由事件确立。
4. **NPC 姓名池规模**：产品文档写"120 姓 × 200/180 名"，落地为 120 × 100/100（组合空间 12000，一局最多 `NPC_MAX = 12` 人，够用）。
5. **叛宗的两句"贡献清零"与"继承 30%"**：按"旧宗门清零、新宗门以旧贡献 30% 起算"落地——唯一让两句同时成立的读法。
6. **首屏拆包方案换路**：原计划"名称表按档位拆 20 个 chunk + 动态 import"。实测否决：名称在 `rollYear` 内被**同步**消费（`encounter.ts` / `artifact.ts`），拆成异步 chunk 就得改造 tick，代价远高于运行时生成。改为「名称表运行时生成 + 内容层整体按需载入」。
7. **`BOND_STRAIN_AFFINITY` 30 → 14**：浏览器实测发现新结识的 NPC 初始好感是 20，而阈值 30 —— 等于每段新关系"一出生就已生嫌隙"，背叛事件立刻可触发。阈值下调到 14（低于初始好感），语义变成"关系被真的搞坏了"（一次带人逃跑 −10 就足以越线）。

### 7.5 踩到的坑

1. **`applyChoice` 只查 `c.events` —— 任务不在里面**。任务被 `acceptMission` 包装成事件后走同一条结算路径，但结算时 `c.events.find(e => e.id === d.eventId)` 找不到它，于是**静默什么都不做**（贡献 +0、日志空）。修法：新增 `sect.eventOrMission()`，`applyChoice` 改用它。这条是「单测写出来了才发现」的典型——不做端到端断言就会一路带进发布。
2. **调度型事件（`weight: 0`）被仲裁顺延后永久丢失**。`arbitrate` 的延迟重试用 `isEligible`，而它对 `weight <= 0` 直接返回 false → 一旦落选就再也回不来。实测后果：5.8 前世道侣只有 466/500 触发。修法两处：重试路径允许零权重（`allowZeroWeight`），`scheduledTick` 补上 `requires` 求值（原先调度型事件的门槛形同虚设）。
3. **大比恒为第 1 名**。`ENEMY_COMBAT` 档位区间是给机缘用的原始战力区间，玩家乘区一开就远超它。见 7.2-2。
4. **新结识的 NPC 一出生就"已生嫌隙"**。浏览器实测才暴露：初始好感 20 < 阈值 30。见 7.2-7。
5. **校验器的反向条件误判**。`not { bondType 道侣 }` 被当成"需要道侣关系"，于是"结为道侣"事件永远被判不可达。修法：`collectNeeds` 带极性（只在肯定位置收集需求），并新增**单一羁绊类型**探针变体；该变体里还**不能**混入其它类型的"结怨"探针（否则 `not { bondType X }` 又被推翻）。
6. **小样本下的统计断言会骗人**。3.1 的 L90 在 600 局下报 5.80（样本 8/7，"未达标"），4000 局下是 4.08（通过）。工具自己打了"样本过少"的提示——**看到小众数先加样本，别先改代码**。
