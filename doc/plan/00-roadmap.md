# 00 · 路线图

## 一、总览

**总估时：单人 25-35 个工作日。** Phase 1 与 Phase 3 风险最高，Phase 5 工作量最大。

| Phase | 主题 | 估时 | 交付状态 |
|---|---|---|---|
| **0** | 脚手架 | 0.5 天 | `npm run dev` 出浅色外壳；`tsc -b` 通过；DOM import 编译失败 |
| **1** | 忠实移植 | 4-6 天 | 参考实现循环完整可玩，零新系统，黄金回归通过 |
| **2** | 决策 + DSL 硬化 | 3-4 天 | 决策闸门上线，60 个事件有真实选项 |
| **3** | 功法 + 战力构成 | 4-5 天 | 六乘区、六流派、共鸣、构筑面板 |
| **4** | 丹药 + 炼丹 | 4-5 天 | 控火小游戏、丹毒、协同 |
| **5** | 宗门 + 羁绊 | 5-7 天 | 八宗门、五羁绊、大比、前世道侣 |
| **6** | 传承 + 洞府 | 4-5 天 | 传承点、洞府六室、图鉴成就、存档迁移 |
| **7** | 平衡、打磨、扩展 | 持续 | 视觉打磨、扩展功法、事件补到 200 |

**每个 Phase 结束时都必须能跑、能判断。没有"纯基建"阶段。**

## 二、依赖关系

```
Phase 0（脚手架）
   │
   ▼
Phase 1（忠实移植）◄──── 最高风险，基线
   │                     分布对不上就停下修，不要往上叠
   ▼
Phase 2（决策 + DSL）◄──── 必须在 3/4/5 之前：新系统的事件都要走决策闸门
   │
   ├──────────────┬──────────────┐
   ▼              ▼              ▼
Phase 3（功法）  Phase 4（丹药）  Phase 5（宗门+羁绊）
   │              │              │
   │   ◄──────────┘              │
   │   3 与 4 有协同（毒体/丹火不侵），需互相引用
   │              │              │
   └──────────────┴──────────────┘
                  │
                  ▼
            Phase 6（传承 + 洞府）◄──── 需要前面所有系统产出结算数据
                  │
                  ▼
            Phase 7（平衡打磨）
```

### 关键依赖说明

| 依赖 | 原因 |
|---|---|
| Phase 2 必须先于 3/4/5 | 新系统的事件都要走决策闸门；先做系统会导致事件要返工 |
| Phase 3 与 4 需并行协调 | 毒体、丹火不侵、万法归一三个协同跨两个系统 |
| Phase 5 依赖 3 | 宗门专属功法需要功法系统 |
| Phase 6 依赖全部 | 传承点公式读取境界/图鉴/宗门/成就/羁绊五类数据 |

## 三、里程碑

| 里程碑 | 条件 | 意义 |
|---|---|---|
| **M1 · 基线可玩** | Phase 1 完成 + 黄金回归通过 | 有了可信的数值基线，后续所有平衡都有参照 |
| **M2 · 决策闭环** | Phase 2 完成 + 单局选项点 ≥25 | 核心痛点之一解决，游戏从"看"变成"玩" |
| **M3 · 构筑成立** | Phase 3 完成 + `P_build/P_nobuild ∈ [2.0,4.5]` | 构筑痛点解决，build 有实际差异 |
| **M4 · 内容自洽** | Phase 4-5 完成 + 全部内容校验通过 | 系统间协同成立（毒体、宗门、羁绊） |
| **M5 · 长期成立** | Phase 6 完成 + 20 世 ≤1.35× | 长期养成痛点解决，且不碾压 |
| **M6 · 发布就绪** | Phase 7 完成 | 视觉、无障碍、内容量全部达标 |

## 四、Phase 1 的特殊地位

**Phase 1 是唯一一个"做不好就必须停下"的阶段。**

理由：后面所有内容（功法数值、丹药效果、宗门俸禄、传承公式）都是**对着 Phase 1 建立的数值基线**调的。如果 Phase 1 的突破曲线、战力增长、机缘档位分布与原作有偏差，那么后续所有平衡工作都建立在错误的地基上。

**验收方式**：

1. **黄金回归**：50 种子 × 200 年，槽 1-9 的 `(最终等级, 最终修为, 命格抽取, 法宝数, 事件 id 序列)` 与基线快照**精确一致**（因为 RNG 流是具名的）。
2. **分位标定**：移植参考实现的 `testLv/testCombat` 分位函数，断言最终等级的 p10/p50/p90 落在 ±8% 内。

**如果分布对不上，停下来修，不要往上叠新系统。**

## 五、风险最高的两个阶段

| Phase | 风险 | 缓解 |
|---|---|---|
| **1** | 转写错误导致数值分布偏移，且很难发现（因为看起来"能跑"） | 黄金回归 + 分位标定双重验证 |
| **3** | 六乘区堆叠导致战力爆炸，或面板与引擎计算不一致 | 每区硬上限 + 软封顶 + `P_build/P_nobuild` CI 断言 + 面板诚实性测试 |

详见 [03-risks.md](03-risks.md)。

## 六、并行化建议

若有多人：

| 可并行 | 说明 |
|---|---|
| Phase 1 内容撰写 | 引擎移植的同时，写手可以并行写 135 个事件的原创文案（用 DSL 格式） |
| Phase 3 与 4 | 功法与丹药可以并行开发，但**协同规则（毒体/丹火不侵）需要接口先对齐** |
| Phase 5 宗门 与 羁绊 | 两个系统相对独立，可并行 |
| Phase 7 视觉打磨 | 任何阶段都可以并行推进 UI 细节 |

**不可并行**：Phase 0 → 1 → 2 是严格串行的，DSL 未定型前写的内容都要返工。
