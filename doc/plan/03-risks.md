# 03 · 风险与对策

按严重度排序。R1 与 R2 是"一旦发生就很难挽回"的类型，优先投入防护成本。

---

<a id="r1"></a>

## R1 · 丢掉机缘的赌博质感

**严重度：最高**

### 风险

参考实现的全部张力来自一个不对称：

```
你看得到 lo-hi 区间，看不到 power
战斗用隐藏 power 判定
逃跑用档差判定（完全另一套规则）
```

三种新系统会破坏它：

| 破坏方式 | 后果 |
|---|---|
| (a) 「剑心通明」把区间收窄到 30% | 赌博变成确定性，玩家不再需要判断 |
| (b) build 战力膨胀到远超机缘档位表 | 每战必胜，遭遇战变成过场动画 |
| (c) NPC 助战堆到 50%+ | 靠人脉碾平战力曲线，赌局消失 |

### 对策

| # | 措施 |
|---|---|
| 1 | **区间收窄硬性上限 50%**，且只能作为气运流（剑修 4 门 + 气运 ≥80）的奖励，不能是默认能力。写成测试断言。 |
| 2 | **机缘档位按玩家 `level` 缩放，绝不按 `power` 缩放**；区间宽度永远保持 `lo = p×0.6-0.9` / `hi = p×1.1-1.5` 的比例，不随等级收窄。写成测试断言。 |
| 3 | **NPC 助战硬上限 30%**，写成测试断言。 |
| 4 | **永远不要做会暴露 `power` 的 UI 元素。** 参考实现的"智能模式按区间中值自动决策"是调试功能漏进了产品——本作把它留在 dev flag 后面且默认关闭；开启时本局禁用成就。 |
| 5 | 类型层面：`enemy.power` 不出现在任何 UI 组件的 props 里。 |

<a id="r2"></a>

## R2 · `luckMult` 被重复应用

**严重度：高**

### 风险

参考实现对四个通道乘 `luckMult = 1 + 气运/1000`（随机事件 / 法宝 / 机缘 / 仙灵气）。本作把幸运敏感通道增加到**六个**（多了宗门事件、羁绊事件）。

陷阱：新系统自己调一次 `luckMult`，调用方槽位又乘一次。结果是气运的收益变成平方——气运流瞬间失衡，而且**很难发现**，因为数值看起来"只是高了一点"。

### 对策（三重防护）

| # | 措施 |
|---|---|
| 1 | **唯一定义点** `src/engine/selectors.ts::luckMult`。写测试 grep `src/engine/**` 断言 `/1000` 只出现一次。 |
| 2 | **`luckMult` 只在 `tick.ts` 的通道掷骰处应用**，绝不在 `events.ts` / `systems/*` 内部应用。ESLint 与代码审查双重把关。 |
| 3 | **每个通道一个单元测试**：气运从 0 翻到 1000，10 万次具名掷骰的触发率必须**精确翻倍（±2%）**。 |

> 第 3 条很便宜，且能永久锁死这个 bug——因为它测的是**行为**而不是**实现**，无论怎么重构都会抓到。

## R3 · 乘区爆炸

**严重度：高**

### 风险

区内加法是必要条件但不充分。真正的失败模式是：**六个乘区在数月的平衡补丁里各从 1.2 爬到 1.6**，没人注意到整体已经膨胀了 5 倍。

这是典型的"温水煮青蛙"——每次改动单独看都合理。

### 对策

| # | 措施 |
|---|---|
| 1 | **每区硬上限写进 `constants.ts`**，在 `power.ts` 里强制。触顶时 dev 模式告警——**某区触顶 = 内容调过头了**，不是"玩家玩得好"。 |
| 2 | **乘积软封顶** `25 × (1 + ln(P/25) × 0.5)`（40× → 36.8×）。这是防"你还没犯的那个设计错误"的兜底。 |
| 3 | **CI 断言四个等级检查点的 `P_build/P_nobuild ∈ [2.0, 4.5]`**。一旦补丁把它推到 5.0，CI 直接失败，你去看乘区表而不是去翻 200 个事件。 |
| 4 | 各乘区 p50 落在预算表 ±20%（`tools/balance.ts`）。 |

> 第 3 条的价值在于**把问题定位到正确的位置**：乘区爆炸的根因在乘区表，不在内容。

<a id="r4"></a>

## R4 · 存档格式迁移

**严重度：中高**

### 风险

系统分 6 个 Phase 加，存档格式至少变 6 次，而玩家**会有进行中的局**。参考实现的存档是散装的 `localStorage` 键值对，没有版本号、没有迁移、没有校验——任何结构变更都会静默丢档。

### 对策（六条硬规则）

| # | 规则 |
|---|---|
| 1 | **带版本信封** `{ v, meta, run, checksum }`，绝不裸存状态 |
| 2 | **迁移链顺序应用**，每步一个 fixture 测试（fixture 必须是**真实导出**，非手写） |
| 3 | **同版本内只增不改**——不原地改名或改语义；加新字段、迁移旧值、旧键留一个版本 |
| 4 | **`RunState` 与 `MetaState` 不共用任何字段名**（有测试断言顶层字段无交集） |
| 5 | 迁移不可恢复时把 blob **归档**到 `xiuxian.save.bak.{v}` 再开新档，**绝不静默丢档** |
| 6 | **节流写入**：只在决策点 + 每 5 年 + 页面隐藏 + 结算时持久化，不要每 tick 写 |

> 第 4 条特别巧妙：因为两个状态不共用字段名，**meta 迁移在结构上不可能污染 run**。这是用命名约定换来的安全性。

<a id="r5"></a>

## R5 · 单局过长 / 操作过碎

**严重度：中**

### 风险

参考实现一局 10-20 分钟（这正是用户想要更多的原因）。但新系统多了 4 个决策面（丹药、宗门、羁绊、功法），失败模式是**"90 分钟一局、60 个弹框"**——玩家的挫败感从"没得玩"变成"玩不完"。

### 对策

| # | 措施 |
|---|---|
| 1 | **harness 强制预算**：单局 25-45 分钟、60-140 年、25-60 个决策。超出 CI 告警。 |
| 2 | **弹框批处理**：每年最多一个，两个系统同时想打断时低优先级顺延次年。优先级已在 tick 槽 14 定死：天劫 > 机缘 > 羁绊 > 宗门 > 丹药。 |
| 3 | **炼丹有跳过与批量**：`mastery ≥ 3` 解锁自动控火；批量炼制消耗 5 份材料只跑一次火。 |
| 4 | **自动策略由玩家预先配置**（规则表："风险 <30% 选激进 / 否则保守 / 遇机缘战力不足则退"）。配置策略本身也是决策，且启用后本局禁用成就。 |
| 5 | **宗门大比与洞府是"界面"而非"打断"**，永不阻塞 tick。 |

> 第 1 条是**可测量的护栏**——不是"感觉上应该控制"，而是 CI 会失败。

## R6 · RNG 流纪律腐化

**严重度：中（但后果严重）**

### 风险

具名 RNG 流只有在被**一致使用**时才有价值。失败模式：

1. 有人在系统里写了裸 `Math.random()`
2. 某个 `chance` 节点用了不唯一的路径 label
3. 确定性静默崩掉
4. 黄金回归开始**间歇性失败**
5. 有人加了 `.skip`
6. **这就是确定性死亡的方式**——一旦允许 skip，确定性就名存实亡

### 对策

| # | 措施 |
|---|---|
| 1 | **ESLint `no-restricted-properties` 在 `src/engine/**` 上禁止 `Math.random`（error 级，不是 warning）** |
| 2 | **`interpret.ts` 是 `rng` 的唯一消费者**；其余系统接收 `RngBag` 参数但不自行取随机 |
| 3 | **CI 里黄金回归不允许 `skip`**——用 `jq` 断言 pending 数为 0 |
| 4 | 一旦不稳定必须**当天修**，不允许靠 skip 让它变绿 |
| 5 | 校验器强制兄弟 `chance` 节点路径唯一 |

> 第 3、4 条是关键：技术防护能防住裸 `Math.random`，但防不住"加个 skip 就好了"的人性。**这条纪律必须写进 CI，不能靠自觉。**

## 风险优先级矩阵

| 风险 | 严重度 | 发生概率 | 防护成本 | 优先级 |
|---|---|---|---|---|
| R1 赌博质感 | 最高 | 中 | 低（3 个断言） | **P0** |
| R2 `luckMult` | 高 | 中高 | 低（1 个测试） | **P0** |
| R3 乘区爆炸 | 高 | 高 | 中（CI 断言） | **P0** |
| R4 存档迁移 | 中高 | 确定 | 中（框架 + fixture） | **P1** |
| R5 单局过长 | 中 | 高 | 中（批处理 + 自动化） | **P1** |
| R6 RNG 纪律 | 中 | 中 | 低（ESLint + CI） | **P1** |

**R1/R2/R3 的防护成本都很低（各一个断言），但一旦失守后果严重**——这是典型的"应该立刻做"的类型。三者都已在 Phase 3/4 的验收标准中固化为测试。

## 已被参考实现验证过的坑（继承的教训）

| 坑 | 参考实现的表现 | 本作的应对 |
|---|---|---|
| 事件是闭包 → 无法调平衡 | 作者只能写 `testLv/testCombat` 分位函数来间接验证 | 效果 DSL + 可统计的内容校验器 |
| `maxCount` 是唯一防重复 | 58 个事件用 `100` 当"无限"哨兵值 | cooldown + recencyQueue + maxCount 三重 |
| 仙界事件漏标 `realm: 2` 静默失效 | `sim.js:492` 是硬池过滤，无任何报错 | 禁止 `realm` 字段，位面门控走 `when`，校验器强制 |
| 名称表跨档重复 23 处 | 手写 1000 条，读起来就是重复 | 组合生成 + 全表精确去重 |
| 法宝是零风险单向棘轮 | 失败无代价、永不丢失、无装备模型 | 保留"失败无代价"（爽点），但引入丹毒作为真实累积代价 |
| 逃跑下限与注释不符 | 注释说 45%，代码实际下限 0 | 以代码行为为准并写入文档 |
| 智能策略变相暴露 power | 调试功能漏进产品 | dev flag + 默认关闭 + 开启时禁用成就 |
