# v0.1.0-03 · Phase 2 决策闸门与 DSL 硬化

> 前置：Phase 1（[v0.1.0-01](v0.1.0-01-scaffold-port.md)）已交付，M1 自洽基线成立。
> 本篇对应 [plan/00-roadmap.md](plan/00-roadmap.md) 的 **Phase 2**，达成里程碑 **M2 · 决策闭环**。

---

## 一、背景与目标

Phase 1 忠实移植了参考实现的"老虎机"循环：事件抽中即结算、玩家旁观，全作唯一的决策点只有机缘弹框。四大痛点之首（**决策太少，全程挂机看结果**）尚未解决。

Phase 2 的目标是把**决策闸门**接进 tick，并让内容层具备"每个事件都是 2-4 个真实取舍"的表达能力与可校验性：

1. **槽 14 弹框仲裁上线**——全年最多产出一个决策，多个来源按优先级竞争，落选者顺延次年（[plan/03-risks.md R5](plan/03-risks.md#r5) 的弹框批处理对策）。
2. **DSL 硬化**——flag 生命周期、cooldown、recency、deferred 全链路生效；`show`/`enable`/`cost`/`hint` 语义可预览且**预览不骗人**。
3. **内容校验器**——135 个事件在 CI 中强制合法（0 error、0 孤儿 flag、可达性采样）。
4. **60 个事件改写为 2-4 个真实选项**——含资源门槛、风险分支与粗略风险提示。
5. **重放确定性**——同种子 + 同选择序列 → 逐字节相同日志，为 Phase 3+ 的万局平衡模拟提供地基。

**非目标**：不新增玩法系统（功法/丹药/宗门/羁绊仍是 Phase 3-6）；不改任何移植红线数值（战力公式、突破表、机缘档位、事件通道 10%、机缘通道 5%/30% 全部不动）。

## 三、技术方案

### 1. 决策闸门（槽 14 仲裁）

```ts
// tick.ts
const PRIORITY = ['tribulation', 'encounter', 'bond', 'sect', 'alchemy', 'world'] as const;

interface Candidate { kind: DecisionKind; eventId: string; decision: Decision }
```

- **事件决策化条件**：事件被抽中时，`show` 通过的选项 ≥ 2 → 产出 `Decision`（`kind` 由 `category` 映射：`world`/`chain`/`fate` → `'world'`，其余同名映射）；只有 1 个选项 → 走 Phase 1 即时结算路径（不算一次决策）。
- **仲裁**：全年所有候选（事件、机缘、天劫各自产出）按 `PRIORITY` 排序，取第一个；其余进 `deferredQueue`。天劫为最高优先级且**不可被推迟**（推迟天劫会改变终局手感）。
- **deferred 顺延**：`DeferredEntry = { eventId: string; year: number }`。次年槽 14 **先重试**上一年的 deferred（此时 `requires` 重新求值，不满足则丢弃），再处理当年候选；延一年仍未触发则丢弃（最多顺延一次，避免僵尸弹窗）。deferred 中的事件 id 在 `pickEvent` 中排除，防止重复抽取。
- **决策间状态冻结**：`awaiting` 非空时 tick 循环停止（store 已实现），决策期间世界不前进——`applyChoice` 之后才继续。

### 2. 「预览不骗人」与确定性

Phase 1 的 `resolveChoice` 会重新求值 `show`/`enable`。事件决策化后这会造成**双重消费**：决策生成时求值一次（`chance` 条件消费 `rng.event`），选择后结算时再求值一次——同一条 `chance` 得到两个答案。

方案：
- **决策生成时固化**：`buildEventDecision()` 用带记忆化的 `EvalCtx` 求值每个选项的 `show`/`enable`/`cost` 可支付性，结果写入 `DecisionChoice`（`show: boolean; enable: boolean; disabledReason?`）。
- **结算时信任**：`resolveChoice(..., { gates: 'trust' })` 跳过 `show`/`enable`/`cost` 的重复求值，直接应用 `cost` 与 outcome 抽取。UI 侧只展示 `DecisionChoice` 的固化结果，`applyChoice` 只接受合法 `choiceId`。
- **RNG 顺序**：`rollYear`（构建决策消费一次）→ `applyChoice`（outcome 抽取消费一次）。重放按同序执行，确定性成立。

`gates: 'eval'` 保留给单选项即时结算路径（无预览，无双重消费问题）。

### 3. flag 生命周期（0 孤儿 flag）

| 机制 | 写入 | 读取 | 清除 |
|---|---|---|---|
| `chain.setsFlag` | 事件结算成功时 `flags[id] = 1` | `{op:'flag'}` 条件 / 下游事件 `requires` | `clearFlag` 效果 |
| `chain.consumesFlag` | — | 同上 | 事件结算成功时 `flags[id] = 0` |
| `setFlag`/`incFlag` 效果 | 效果执行时 | 同上 | `clearFlag` 效果 |

校验器将三类写入方与两类读取方做**全量交叉检查**：读到的 flag 无任何写入 → error（孤儿读）；写入的 flag 无任何读取 → warning（死代码）。

### 4. 重放

```ts
export interface DecisionRecord {
  year: number;
  kind: DecisionKind;
  eventId: string;
  choiceId: string;
}

export function replayRun(
  content: ContentBundle,
  opts: SimOptions,
  decisions: DecisionRecord[],
): SimOutcome;   // 遇 record 与 pending 不匹配 / 日志分歧 → 抛错，不静默继续
```

- `RollYear` 产出 pending 时按序消费一条 record；`eventId`/`year` 不匹配即抛。
- 重放结束后逐行比对 `LogLine`（`JSON.stringify` 全等）与终态摘要；首个分歧处抛错并打印上下文。
- `simulate()` 内部走同一条代码路径（自动应答 + 记录），保证"记录→重放"闭环自证。

### 5. AutoPolicy（无头应答）

| 决策类 | 默认应答 |
|---|---|
| 事件 | `first`（第一个 `show && enable` 的选项）；`--policy random` 可切换 |
| 机缘 | 现有 `battlePolicy`（sim 默认 `manual` → 应答 `fight`） |
| 天劫 | `continue` |
| 抽卡 | 现有 `drawCard` |

策略是**模拟器参数**，不进引擎——引擎只认 `choiceId`。

### 6. `--pacing` 双口径

```
决策次数   = 事件决策 + 机缘 + 天劫 + 开局抽卡
选项点总数 = Σ 每次决策展示的可见选项数
```

- **验收口径为选项点总数**（对齐 [00-overview.md](product/00-overview.md) 「480 个决策点 = 200 事件 × 平均 2.4 选项」的定义）。
- 两个数都如实输出；`决策次数` 供后续 Phase 对照。Phase 2 的实测约 14 次/局、选项点约 28/局（差额来源见 §六 R2）。

**60 个事件的分配与原则**：mortal early 18 · mid 20 · late 12 · immortal lower 7 · upper 3。

- 按 `weight` 由高到低选取（玩家遇到最多的事件优先改）；
- 每事件 2-4 个选项，**至少一个选项带 `enable` 门槛或 `cost`**（否则不是真实取舍）；
- 选项必须构成**不同类型的取舍**（资源换收益 / 风险换上限 / 即时换长期），禁止"是/否"伪选择与"明显更优项"；

- 不改 `tier/weight/levelMin/levelMax/cooldown`（保持抽取分布稳定）；
- 改写事件的首个选项尽量保留原结局方向（减小基线漂移，见 §六 R1）。

## 六、风险与对策

<a id="r1"></a>

### R1 · 黄金基线必须重建（必然发生，非回归失效）

**事实**：60 个事件的 outcomes 结构被改写 → 事件结算消费的 `rng.event` 序列改变 → 下游所有随机量错位。`tests/fixtures/{golden,calibrate}.json` 必然变化。

**为什么要重建而不是回退**：改写后的基线仍满足"槽 1-9 的值由具名 RNG 决定、可精确复现"的**自洽**性质（M1 的定义，见 [v0.1.0-01](v0.1.0-01-scaffold-port.md) 偏差 1）。改写内容是 Phase 2 的验收要求本身，不重建就无法交付。

**对策**：
1. 重建前先跑一次**未改写基线对照**：记录新基线相对旧基线的分位偏移量，确认偏移只来自事件通道（突破/法宝/机缘/灵气通道的曲线形状不变）；
2. 分位标定（calibrate）保持 ±2% 回归口径，但明确标注"对照 Phase 2 自身基线"；
3. 在交付记录中写清偏移量与归因。

<a id="r2"></a>

### R2 · 决策密度口径（已与用户确认）

**事实**：事件通道 10%/年、机缘 5%（跨境界 30%）是移植值；一局 90 年实测 ≈ 8.6 次事件 + 4.8 次机缘 + 0-3 次天劫 ≈ **13-16 个决策机会**。[00-overview.md](product/00-overview.md) 的「25-60 个真实决策」是全系统齐备（Phase 3-6 的功法/丹药/宗门/羁绊各自带决策面）后的目标。

**对策（用户裁定）**：`--pacing` **双口径如实输出**；验收按**选项点总数 ≥ 25**（对齐文档自身对"决策点 = 选项"的定义）；决策次数如实记录，差额归因写明。不改任何移植数值。

<a id="r3"></a>

### R3 · 预览骗人（`chance` 节点双重消费）

决策生成与结算各求值一次 gates → 同一 `chance` 两个答案。

**对策**：§三.2 的"生成时固化 + 结算时信任"；测试断言：构造一个 `show: {op:'chance'}` 的事件，决策展示的 `show` 与最终结算分支一致（同一 seed 下重复 100 次）。

<a id="r4"></a>

### R4 · deferred 与 maxCount/recency 的相互作用

被推迟的事件若已计入 `maxCount`/`recencyQueue`，会污染后续抽取；若不计，则可能被当年 `pickEvent` 再次抽中造成双份。

**对策**：推迟时不记任何触发状态；`pickEvent` 排除 deferred 中的 id；deferred 条目最多顺延一次（延后一年仍未触发则丢弃）。三条都有单测。

<a id="r5"></a>

### R5 · 单选项与多选项事件混存的确定性

只有 1 个可见选项的事件走即时结算，≥2 个走闸门。若某事件的选项数**依赖运行时状态**（`show` 条件），同一事件在不同局会走不同路径——这是合法设计，但校验器需检查 `show` 条件不会让事件"有条件地变成 0 选项"（error）。

**对策**：校验器断言每个事件**至少 1 个无条件 `show` 的选项**（永远可结算）。

<a id="r6"></a>

### R6 · 可达性检查的成本与误报

「500 采样状态每个事件至少触发一次」需要无头模拟采样。rare 事件（`tierMin: 4`、`weight` 低、高 `levelMin`）可能采不到。

**对策**：采样用分层策略（10 档卡片 × 长年限 × 多种应答策略），不可达清单先输出为**独立报告**；真不可达才报 error。阈值与采样量在实现时按实测校准，写进交付记录。

### 2. R1 基线重建：偏移量与归因

**重建方式**：内容改写落地后以 `sim:golden:write` / `sim:calibrate:write` 覆盖两个 fixture。

**归因 A/B 对照（收尾补做）**：取 HEAD（Phase 1）代码与当前代码，在同一批 20 种子 × 120 年上跑探针：

- **关闭事件通道（`events: []`）时两树输出逐字节一致**（等级 / 修为 / 仙灵气 / 法宝数 / 日志行数全等）→ 突破表、法宝、机缘、灵气、寿元等**非事件通道零改动**；
- 开启事件通道后 20/20 全部不同 → 偏移确由事件通道（内容改写 + 决策闸门）引起。

**偏移量（golden，50 局 × 200 年）**：平均绝对修为偏移 **4.79%**，最大 **−86.3%**（`golden-001`：44044 → 6013，等级 49 → 48），最大等级偏移 −3。
**偏移量（calibrate，每档 200 局）**：分位偏移最大 **±4%**（tier5 p50 `51→49`、tier2 p90 `25→26`）；档位曲线形状不变（p50 序列 14/22/31/41/49/61/69/75/83/85）。注意 ±2% 是 `--calibrate` 的**比对容差**，不是分位偏移幅度。

**归因**：改写事件的首个选项虽尽量保留原结局方向，但闸门把「事件抽中即结算」变成「选项 ≥2 时停住等玩家」；自动应答取第一个可选项，单局收益路径因此改变。偏移幅度与事件的 `weight` 正相关（被改写的高权重事件遇到得最多）。

### 3. R2 决策密度归因（如实输出）

选项点 p50 = **31**（≥ 25 达标），决策次数 p50 = **12**（均 12.5）。差额来源：一局 90 年实测 ≈ 8.6 次事件 + 4.8 次机缘 + 0-3 次天劫。`product/00-overview.md` 的「25-60 个真实决策」是全系统齐备（Phase 3-6 的功法/丹药/宗门/羁绊各自带决策面）后的目标。**未改任何移植数值**。

### 4. R6 可达性采样的实测阈值

校验器探针把 `chance`/`roll` 视为「可能通过」，只检验其余门槛；采样状态集覆盖 10 档卡片 × 长年限 × 多种应答策略。实测 **135/135 事件可达，不可达清单为空**，未出现误报，无需放宽阈值（`--no-reach` 可跳过该检查）。
