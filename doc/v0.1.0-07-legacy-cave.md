## 一、背景与目标

Phase 5 交付记录里明确留给 Phase 6 的有两条线：

1. **Z5 缺口（宗门药材俸禄）的 L70/L90 余量**——L70 −32% → −23%、L90 −43% → −21%，仍是「阶段性缺口」，需要在 3.2 里复验。
2. **`balance.ts` 的 `GAPS.z1 = [90]`**——注释里写的就是「Z1@L90 含静室（Phase 6）」。静室一落地，Z1@L90 就该从 gap 变成真断言。

但 Phase 6 真正的分量不在复验这两条，而在**跨局层本身**。这是整个项目的 M5 里程碑：

| 里程碑 | 条件 | Phase 6 的位置 |
|---|---|---|
| M5 · 长期成立 | 20 世 ≤ 1.35× | **本 Phase 的出口条件** |

四个交付目标：

1. **传承点可结算、可花**（验收 6.1/6.2/6.3）——局末按公式结算传承点，洞府六室按 `1.6^n` 升级，收益是"起跑线更高"，不是"上限更高"。
2. **防碾压在设计上成立**（验收 6.1）——第 20 世最终等级 ≤ 第 1 世的 1.35×。这是本 Phase 最难的一条，且必须在**设计上**成立（[product/08-legacy-cave.md §四](product/08-legacy-cave.md#四防碾压设计)），不能只靠事后调参。
3. **跨局层有内容**（P1）——约 80 个成就、图鉴位串、高光记录、本地三榜。
4. **存档链完整**（验收 6.4-6.9）——迁移 v5→v6，每个版本都有真实 fixture；校验和、失败归档、节流写入、字段不冲突、存档体积。

**Phase 6 是最后一个"新系统 Phase"**（Phase 7 只剩打磨与扩量），所以它也是唯一一次能把跨局层一次性设计对的机会。

## 三、技术方案

### 1. 洞府注入：唯一的引擎入口是 `RunState.cave`

6.3 红线禁止引擎 import `MetaState`（`types/meta`），所以洞府等级走 `pastPartner` 已验证过的注入路径：

```
MetaState.cave  ──(store / simlib 边界)──▶  RunOptions.cave
                                             ──▶ createRun opts.cave
                                                     ──▶ RunState.cave
                                                             ──▶ cave.ts 唯一读取点
```

`RoomId` / `CaveLevels` 落在 `types/run.ts`（引擎侧），`types/meta.ts` 从 `./run` 再导出——**一处定义，引擎不反向依赖**。

六个效果各自只读自己那一个房间，互不串扰：

| 房间 | 引擎读取点 | 效果 |
|---|---|---|
| 药园 | `tick.ts` 新槽 `caveTick` | 每年 `等级` 株药材（**确定性轮转，不抽 RNG**） |
| 丹房 | `alchemy.schoolBonusOf` | 品质 `+等级 × 0.15` |
| 藏经阁 | `arts.insightCostFor` | 功法升级悟性 `−等级 × 5%` |
| 悟道室 | `arts.slotCount` + `selectors.insightPerYear` | L2/L4 各补 1 槽；`+等级 × 0.5` 悟性/年 |
| 聚灵阵 | `selectors.zones()` z1 | Z1 `+等级 × 4%` |
| 静室 | `selectors.zones()` z1 + `tick.ts` | Z1 `+等级 × 5%`；模拟点消耗 `−等级 × 0.5%` |

**Z1 封顶校验（6.2）**：聚灵阵 + 静室 满级合计 +45%，Z1 硬上限 ×3.0，功法侧还能再叠——封顶必然生效，不存在"洞府把 Z1 顶穿"的可能。

**药园不抽 RNG**：`caveTick` 用 `s.year % 6` 在六种基础药材间轮转。理由是黄金回归（1.1）逐字节比对 50 种子 × 200 年，只要多抽一次就全线漂移；而洞府等级为 0 时本槽**直接 return**，连一次取模都不做。

### 2. 静室的"模拟点消耗"收窄到掠夺消耗 —— 主动偏离原设计

**产品文档原文**：「静室：Z1 `+等级 × 5%`，模拟点消耗 `−等级 × 0.5%`」。

按字面实现会直接违反 6.1。`simPoints` 在本项目里就是**寿元**（`age > simPoints` 即死），把它整体调低 = 直接买等级 = 传承碾压的教科书路径。Phase 5 的 5.1 判据正是被同一条"资源最终折成等级"的闭环逼到改口径的（比值 2.696），这里是同一个坑第二次出现。

**实施口径**：静室的减免只作用于**每年额外消耗**的模拟点，即魔修协同的 `plunderDrain`，不碰基础寿元。理由：

- 保留了"洞府能缓解 build 代价"的设计意图（带 4 门魔修时装机更有价值）；
- 不动寿元预算 → 等级上限与判定链完全不受洞府影响；
- 与 [product/08-legacy-cave.md §四·2](product/08-legacy-cave.md#四防碾压设计)「核心难度曲线完全不随传承变化」一致——寿元就是难度曲线的一部分。

代价：静室对非魔修 build 是纯 Z1 加成。**如实记录，不假装它对所有 build 都好用。**

### 3. 传承点公式（`src/engine/meta.ts`）

按 [product/08-legacy-cave.md §一](product/08-legacy-cave.md#一传承点) 的公式实现：

```
境界分 = floor(历史最高等级 / 5)
飞升分 = 飞升次数 × 50 + 证道次数 × 50
图鉴分 = floor(图鉴收集总数 / 20)
宗门分 = Σ(各宗门历史最高职位 × 15)
成就分 = 成就数 × 2
羁绊分 = 道侣羁绊等级 × 10 + 历史羁绊总数 × 2
叛宗系数 = defections > 0 ? 1.15 : 1
```

`legacyPointsOf(src)` 接收一个**普通结构体** `LegacySources`，不 import `MetaState`；`settle` 由 store 层负责把 `MetaState` + `SimOutcome` 组装成 `LegacySources`。这样 6.3 的源码扫描对 `src/engine/meta.ts` 同样成立。

洞府升级成本 `base × 1.6^level` 四舍五入到整数，六室 base = 20/25/30/35/30/40，满级总成本 2846（与产品规格一致）。

### 4. 局末结算

当前 `afterTick` 检测到 `ended` 就只写存档，**没有任何跨局写入**。本 Phase 补一条完整路径：

```
rollYear → ended
  └─▶ store.settleRun(outcome)
        ├─▶ meta.totals.{runs,years,ascensions,zhengdao,bestLevel} 累加
        ├─▶ meta.sectLegacy[sectId] = max(历史, run.sect.rank)
        ├─▶ meta.pastLives.unshift(LifeSummary)  保留最近 20 条
        ├─▶ meta.pastPartners.unshift(partnerOnRunEnd(run))
        ├─▶ meta.unlocks.{arts,recipes,sects}  ∪
        ├─▶ meta.codex 六位串 |= 本局遇到的条目
        ├─▶ 成就判定（achievements.ts）→ meta.achievements ∪ 新解锁
        └─▶ legacyPointsOf(...) → meta.legacyPoints += total
                                                    meta.lifetimeLegacy += total
```

**下一局的注入**（`chooseStarter`）：`cave`、`pastPartner`、`goldBoost`（成就累计的气运抽取加成）三样从 `meta` 取出塞进 `createRun` / `drawCard`。这是 6.3 的边界。

### 5. 图鉴与成就

**图鉴**用位串（`orBits`）跨局累积，六个位串对应 [product/08-legacy-cave.md §五](product/08-legacy-cave.md#五图鉴成就高光排行榜) 的六张图鉴：机缘 / 法宝 / 境界 / 丹药 / 功法 / 药材。当前 `CodexBits` 只有三张，v6 迁移补齐后三张。

**成就**约 80 个，分九组（灵根与境界 / 个人修为 / 法宝 / 总战力 / 渡劫 / 飞升成仙 / 仙界篇 / 图鉴 / 宗门羁绊传承）。每个成就给 `bonus`（气运抽取的百分点），累加后作为 `drawCard` 的 `goldBoost`。

**成就的 crusher 风险**：`goldBoost` 抬高气运档位权重 → 更高气运 → `luckMult` → 机缘/法宝概率。气运本身不进 `breakChance`（进的是 `talentMult`/`thunderBreakMult` 之类），但会走 `luckMult(s)` 影响事件密度。**必须由 6.1 实测裁决，不能想当然。**

### 6. 验收 6.1 的实测装置

`tools/sim.ts --lives 20`：

```
for life in 1..20:
  cohort(cave = 当前洞府等级, goldBoost = 累计成就加成, pastPartner = 上世道侣)
  → 结算传承点 → 贪心升级洞府（按"每级收益/成本"降序）
打印逐世：洞府总等级 / 传承点余额 / 最终等级 p50 / 总战力 p50
判据：L20 最终等级 p50 ≤ L1 最终等级 p50 × 1.35
```

贪心升级的排序需要一张**每级边际收益表**，按"Z1 乘区贡献 / 成本"估：聚灵阵与静室直接进 Z1，悟道室给槽位（槽位是离散的，按"多一个槽能多装一门"的估值），药园/丹房/藏经阁走资源侧。

### 7.2 推翻了设计假设：**成就只能买气运，不能买灵根**

**这是本 Phase 最重要的一条，也是"看起来该 work 但没 work"的典型。**

第一版 `drawCard` 把 `goldBoost` 同时喂给**灵根**档位抽取与**气运**档位抽取（`pickTier(rng, goldBoost, ...)` 两处都传）。产品文档写的是"每个成就给**高阶气运抽取概率加成**"，但实现顺手把灵根也加权了。

后果：灵根档 → `talentMult` → **突破概率**。也就是说成就直接买的是难度曲线本身。二十世实测：

| 版本 | 等级 p50（第 1 世 → 第 20 世） | 比值 | 判据 |
|---|---|---|---|
| `goldBoost` 同时加权灵根 | 53 → 79 | **1.491** | ✗ 破线 |
| `goldBoost` 只加权气运 | 53 → 61 | **1.151** | ✓ |

隔离实验（同 60 局、洞府全 0、固定种子）：

| 变量 | 灵根 p50 | 气运 p50 | 等级 p50 | 等级比值 |
|---|---|---|---|---|
| 基线 | 107 | 86 | 61 | 1.000 |
| `goldBoost = 6` | **140** | 105 | 69 | **1.131** |
| `goldBoost = 12` | **155** | 109 | 69 | 1.131 |
| 修掉之后 `goldBoost = 12` | 107 | **109** | 61 | **1.000** |

**洞府本身完全无辜**：六室逐间拉满的隔离实验，最高只有 `悟道室 L5 = 1.066`，六室全满 `+ goldBoost=12` 合计 **1.049**。真正的碾压源是成就加成的落点，不是洞府。

**改法**：`drawCard` 的灵根档位改回 `pickTier(rng, 0, guard)`，`goldBonus` 只进 `luckTier`。副作用检查：`goldBoost` 默认为 0 时两条路径完全等价，**黄金回归逐字节不变**（已实测）。

顺带补上 `ACHIEVEMENT_BONUS_CAP = 12` 的总量封顶。

### 7.3 主动收窄：静室的「模拟点消耗」

产品文档原文是「模拟点消耗 `−等级 × 0.5%`」。按字面实现会**直接违反 6.1** —— `simPoints` 在本作里就是寿元（`age > simPoints` 即死），整体调低等于直接买等级。

这和 Phase 5 的 5.1 是**同一个坑的第二次出现**：引擎里所有资源最终都会折成等级（俸禄悟性 → 战力 → 机缘胜率 → 灵根 → 突破表行 → 寿元）。Phase 5 已经在那里栽过一次（比值 2.696，被迫改判据）。

**实施口径**：静室的减免只作用于**每年额外消耗**的模拟点（魔修协同的 `plunderDrain`），不碰基础寿元。理由写在 `cave.ts` 的 `plunderRelief` 注释里。

**代价如实记录**：静室对非魔修 build 是纯 Z1 加成（+5%/级），不再有"延寿"这一层。

### 7.4 6.8 逼出的改名：`RunState.cave` → `RunState.legacyCave`

洞府等级要同时存在于两处：跨局层 `MetaState.cave`（持久，权威）与 `RunState`（本局注入，引擎只读）。第一版两边都叫 `cave`，**直接撞上 6.8「顶层字段名无交集」**。

改成 `RunState.legacyCave`，名字本身就标出了 6.3 的边界：它不是状态，是边界层注入的**只读视图**。`RunOptions.cave` / `createRun(opts.cave)` 的对外参数名不变。

### 7.5 洞府升级不落盘（浏览器实测抓到的 bug）

在浏览器里点「升级 · 25」，界面从 420 变 395、丹房 L0→L1，**但 `localStorage` 里的洞府等级纹丝不动**。原因：存档器 `saver` 是 `runStore` 的模块级私有对象，而升级动作发生在 `useMetaStore` 里，两边没有连接。

改法是订阅而不是反向依赖（反向 import 会成环）：

```ts
useMetaStore.subscribe(() => saver.request());
```

浏览器复测：升级 → 刷新 → 洞府等级与传承点余额都正确落盘。

### 7.6 Phase 5 留的两条余量：复验结果

**Z1@L90**（`balance.ts` 的 `GAPS.z1 = [90]`，注释写「含静室（Phase 6）」）：

| 群体 | L30 | L50 | L70 | L90 |
|---|---|---|---|---|
| 无洞府（3.2 现行口径） | 1.38 | 1.50 | 1.63 | 1.90（预算 2.4，−21%） |
| 六室满级 | 2.08 | 2.08 | 2.38 | **3.00**（预算 2.4，+25%） |

洞府把 Z1 推离预算中心（+25%）属预期——洞府是起跑线不是上限。关键是 **3.00 正好是硬上限，一个都没越**（验收 6.2 逐档断言）。`GAPS` 里 `z1: [90]` 保持原样：3.2 仍是无洞府基线口径，另开「洞府复验」段对照。

**Z5@L70/L90**（Phase 5 留的「余量留给 Phase 6 药园复验」）——**药园没有关掉这个缺口，反而让 Z5 更低了**：

| 群体 | L30 | L50 | L70 | L90 |
|---|---|---|---|---|
| 无洞府 | 1.03 | 1.20 | 1.12（−23%） | 1.33（−22%） |
| 六室满级（含药园 L5） | 1.02 | 1.06 | 1.12（−23%） | **1.17（−31%）** |

**根因**：药材多了 → 能炼更多丹 → **丹毒也涨** → Z5 里的 `−毒性/250` 惩罚项把药力吃掉一部分。药园不是平摊的 Z5 供给，它喂的是毒修那条「刻意嗑低品质把丹毒顶满 → 毒体」的打法。已在 `product/08-legacy-cave.md §二` 写明，并保留在 `balance.ts` 的输出注里。

> 顺带记一个**没有交付**的东西：本来想加一条「药园 × 毒体」的对照来验证上面的解释，实测两个「无洞府」对照组 200 年都到不了 L90（样本 0），断言被静默跳过。**跑出 0 样本的对照不交付**，已删除，结论只以文字形式记在这里。要坐实这个解释需要一条更长的队列或 Phase 7 的 P2 项。
