# 修仙模拟器 · 文档库

本目录是项目的**唯一权威文档源**。代码可以重构，文档必须同步——文档与实现冲突时，先改文档再改代码。

---

## 一、这是什么项目

一个中文网页修仙人生模拟器。玩家抽灵根/气运/命格入道，逐年修行，历经机缘、法宝、丹药、宗门、羁绊，渡九重天劫飞升仙界，最终证道成圣。

玩法模型借鉴自 `https://xiuxian.hidewnd.cn/`（下称**参考实现**），但**代码与文案全部原创**。我们在其核心循环之上补了四块深度：真实决策、构筑 combo、长期养成、内容体量。

一句话概括差异：**参考实现是一场你可以观看的老虎机；本作是一场你可以操作的赌局。**

### v0.1.0 偏差记录

建库时相对原计划的偏差，如实记录：

| 计划 | 实际 | 原因 |
|---|---|---|
| 写手手册放 `docs/event-authoring.md` | 放 `doc/guides/event-authoring.md` | 原计划同时存在 `doc/` 与 `docs/` 两个近同名目录，人极易混淆、工具链也容易误配。统一收进 `doc/` 文档库，用 `guides/` 子目录区分读者（开发者 vs 内容写手） |

| 版本号从 `v0.1.0-01` 起 | 文档库本身记为 `v0.1.0`，Phase 0-1 记为 `v0.1.0-01` | 代码未写、文档先行，需要一个"文档库建立"的版本锚点 |
| — | 在 `03-risks.md` 与 `00-overview.md` 加显式 `<a id="...">` 锚点 | GitHub 对中文标题的 slug 会残留标点转换结果（`## R1 · xxx` → `r1--xxx`），短锚 `#r1` 无法命中。用显式 HTML 锚点固定短锚，比长中文 slug 稳定 |

## 五、写作约定

### 文档模板

新增**增量实施文档**（`v0.1.0-NN-*.md`）时，必须遵循统一模板：

1. **背景与目标** —— 为什么要做这件事
2. **现状与改动文件** —— 涉及哪些文件，从什么状态改到什么状态
3. **技术方案** —— 含对生产包体的增量预算标注（KB）
4. **任务拆解** —— P0/P1/P2 分级 + 依赖关系
5. **验收标准** —— 可测试、可演示
6. **风险与对策**
7. **交付记录** —— 末尾回填，**如实记录踩到的坑与偏差，不只写成功路径**

产品/技术 wiki 是**长期文档**，不套用上述模板，但必须保持结构一致、交叉引用有效。

### 交叉引用

- 文档之间用相对路径链接，如 `[效果 DSL](tech/02-effect-dsl.md)`。
- 引用具体代码位置时写 `路径:行号`。
- **术语必须与 [00-overview.md 术语表](product/00-overview.md#术语表) 一致**。新增术语先加表再用。

### 数值变更

任何数值改动（概率、倍率、阈值、上限）必须同时改文档与代码，并在增量文档的交付记录里写明**改了什么、为什么改、影响哪些验收断言**。数值散落在文档里是刻意的——文档是调平衡时的唯一参照面。

### 如实记录

文档的价值在于记录**真实发生的事**，包括：
- 与原计划偏离的地方，以及偏离原因
- 踩到的坑（尤其是"看起来该work但没work"的）
- 被推翻的设计决策，以及被推翻的证据

只写成功路径的文档等于没有文档。
