## 一、背景与目标

文档库已定稿 22 篇、代码零行。整个工程的第一个风险不是"功能写不出来"，而是**文档里的工程约束只是文字**——尤其是"引擎必须是纯 TS，零 DOM / 零 React"这条。它靠自觉必然腐化：某天有人为了省事在 `src/engine/` 里读一次 `localStorage`，确定性、可测试性、无头模拟同时崩掉，而且**编译器不会报错**。

Phase 0 的唯一目的：**把文字约束变成编译器与 CI 强制的事实**，并把深色外壳立起来作为后续所有 UI 的视觉基准。

### 目标（可判定）

| # | 目标 | 判定方式 |
|---|---|---|
| 1 | 引擎纯净由编译器强制 | 故意 import `localStorage` 的 engine 文件**编译失败** |
| 2 | 工程骨架可跑 | `npm run dev` 出深色外壳；`tsc -b` 通过；`npm test` 通过 |
| 3 | 视觉基准落地 | `tokens.css` 全量 token + `base.css` 动画词表，外壳消费它们 |
| 4 | RNG 纪律的二级防线就位 | ESLint 在 `src/engine/**` 上禁 `Math.random`（error 级） |

### 非目标（本批次明确不做）

- 不写任何引擎逻辑（`rng.ts` / `tick.ts` / `interpret.ts` 全在 Phase 1）
- 不写任何事件内容（135 个事件全在 Phase 1）
- 不引入路由、动画库、UI 组件库、Web 字体、虚拟列表（理由见 [tech/00-project-setup.md §二](tech/00-project-setup.md#二依赖清单)）
- 外壳里的资源条与日志流是**硬编码演示数据**，Phase 1 才接真实 tick

## 三、技术方案

### 3.1 依赖版本选择

| 依赖 | 版本 | 说明 |
|---|---|---|
| `react` / `react-dom` | 19.3.x | 视图层 |
| `zustand` | 5.0.x | tick 循环必须在 React 渲染周期外读写状态 |
| `immer` | 11.1.x | Zustand middleware，结构共享 |
| `typescript` | **5.9.x（不用 7.0）** | 见下方决策 |
| `vite` | 8.3.x | 构建与 dev server |
| `@vitejs/plugin-react` | 6.1.x | React 支持 |
| `vitest` / `@vitest/coverage-v8` | 5.0.x | 测试；`test.projects` 双 project |
| `tsx` | 4.23.x | 运行 `tools/` 下 node 脚本 |
| `jsdom` | 30.1.x | ui project 环境（文档依赖清单遗漏，本次补入） |
| `eslint` + `@eslint/js` + `typescript-eslint` + `globals` | 10.x / 10.x / 8.70.x / 17.x | R6 二级防线 |

**决策 1：TypeScript 用 5.9 而非 7.0。** 2026-09 时点 `typescript@latest` 已是 7.0.2（原生编译器），但 `typescript-eslint@8.70` 的 peer 范围是 `>=4.8.4 <6.1.0`——**上 TS 7 就等于放弃 ESLint**，而 R6（RNG 流纪律）的二级防线依赖 ESLint。脚手架阶段稳定优先，锁 `~5.9.3`；待 typescript-eslint 支持 TS 7 后再单独立项升级（升级本身有独立验收：`tsc -b` 通过 + 纯净探针仍失败）。

**决策 2：ESLint 用 flat config（`eslint.config.js`），不建 `.eslintrc.json`。** 文档 [tech/05-toolchain.md §三](tech/05-toolchain.md#eslint-配置关键规则) 写的是 `.eslintrc.json`，但 ESLint 10 已移除 eslintrc 支持，flat config 是唯一形态。规则内容与文档完全一致，仅文件名与格式变化。

### 3.2 编译器强制引擎纯净（本 Phase 的核心）

三重硬失败来自 `tsconfig.engine.json` 的 `lib: ["ES2022"]` + `types: []`：

1. `document` / `window` / `localStorage` / `setTimeout` 全部是未声明标识符 → **TS2304**
2. `import ... from 'react'` 能解析但 React 类型与 JSX 缺失 → 实际使用即错误
3. `localStorage` 未声明 → **持久化必须待在 `src/store/`**，这是编译器保证的事实

实现要点（文档没写、但落地必须处理的）：

- `composite: true` 与 `noEmit: true` 在 TS 5.9 下的组合行为需实测；若不兼容，退化方案是 `composite: true` + `emitDeclarationOnly: true` + `declarationDir` 指向 `node_modules/.tmp/`
- `tsBuildInfoFile` 一律指向 `node_modules/.tmp/`，避免 `.tsbuildinfo` 污染仓库根
- app 项目通过 `references` 引用 engine 项目，`tsc -b` 保证 engine 先编

### 3.3 Vitest 双 project

`test.projects` 两个 project：engine 跑 node（快、无 DOM）、ui 跑 jsdom。覆盖率门槛（lines 90 / functions 90 / branches 85）**只挂在 engine 上**——UI 的覆盖率没意义，行为测试更有价值。

Phase 0 的 `src/engine/` 是空的，覆盖率门槛只在显式 `npm run coverage` 时生效；`npm test` 不触发阈值。

### 3.4 视觉外壳

- `tokens.css` 只放变量，**零选择器**；`base.css` 只消费 `var(--*)`，**零字面量颜色**
- 氛围层（云涌渐变 + 噪点 + 星野）走 `body::before/::after`，零图片、零网络
- 动画词表（`凝气` `流光` `灵光` `翻页` `碎裂` `飞升` `顿悟` `丹火` `云涌` `劫雷`）在 `base.css` 具名定义，组件只引用名字
- 假日志流：脚本化的 20 余行演示日志按 ~1.1s 逐行追加，**渲染侧只渲染最后 120 行**、每行 `content-visibility: auto`——把 Phase 1 日志流的性能约束提前固定下来
- 布局：移动端单列 480px + 底部导航 56px（含 `env(safe-area-inset-bottom)`）；桌面端 `220px minmax(0,1fr) 320px` 三栏
- `prefers-reduced-motion: reduce` 全量关闭动画（硬要求）

### 3.5 生产包体增量预算

实测（`npm run build`，2026-09-24）：

| 产物 | 本批次增量 | gzip | 说明 |
|---|---|---|---|
| JS（React 19.3 + ReactDOM + 外壳） | 225.6 KB | 71.2 KB | zustand / immer 未被外壳引用，构建时被 tree-shake（产物中 0 命中） |
| CSS（tokens + base） | 12.2 KB | 3.8 KB | 含氛围三层（约 1.5 KB）与全部动画词表 |
| HTML | 0.6 KB | 0.4 KB | |
| 引擎 + 内容 | 0 | 0 | Phase 1 |
| **合计** | **238.4 KB** | **75.4 KB** | 首屏目标 < 200 KB gzip，余量约 125 KB |

**偏差：** 立项时估 React 栈 ~180 KB / 58 KB gzip，实测 JS 达 225.6 KB / 71.2 KB——React 19.3 的运行时比预算大。首屏目标仍有充足余量，但 Phase 1 引入引擎与内容后需要重新核对；若逼近 200 KB，先拆名称表（[tech/00-project-setup.md §五](tech/00-project-setup.md#五构建产物预算)）。

## 六、风险与对策

| # | 风险 | 对策 |
|---|---|---|
| P0-R1 | **探针"假失败"**：`tsc -b` 增量缓存导致删掉探针后仍报错，或探针没被真正编译而误判通过 | 探针验证分三步：① 写入探针 → `tsc -b` 必须失败（记录完整错误）② 删除探针 → 清 `node_modules/.tmp/` 下 buildinfo → `tsc -b` 必须通过 ③ 再跑一次 `tsc -b` 确认稳定 |
| P0-R2 | **大版本漂移**：Vite 8 / Vitest 5 / ESLint 10 / TS 7 全是最新大版本，配置写法可能已变 | 版本在 `package.json` 锁 minor；每步装完立即跑对应命令，失败就地降级到上一个 major（降级记录进交付记录） |
| P0-R3 | **`composite` + `noEmit` 组合不受支持** | 退化方案：`composite` + `emitDeclarationOnly` + `declarationDir: node_modules/.tmp/types`；仍不行则放弃 project references、改用单一 `tsconfig.json` + 独立 `tsconfig.engine.json` 由 `npm run typecheck` 串联（**这会削弱 0.2 的自动性，必须记录**） |
| P0-R4 | 假日志流被误当引擎输出，后续有人往上接真逻辑 | 演示数据集中在一个 `DEMO_LOG` 常量里，文件头注释标明"Phase 1 由 tick 替换"；不做任何状态耦合 |
| P0-R5 | 包体超预算（React 19 + 依赖） | 首次 `npm run build` 后核对 gzip 体积；超 200 KB 则把名称表拆分方案提前（[tech/00-project-setup.md §五](tech/00-project-setup.md#五构建产物预算)） |

#### 踩到的坑

1. **覆盖率门槛"假通过"。** engine 目录为空时，空模块是 0/0 行，被判定为达标——`npm run coverage` 退出码 0，看起来门槛在工作，实际什么都没拦。用含未覆盖分支的探针文件验证后才确认门槛真的会拦（3 条 ERROR、退出码 1）。**"空目录下通过"不能当作门槛生效的证据。**
2. **覆盖率配置位置靠插桩才定位到。** 表面现象是"thresholds 配了不生效"；往 `@vitest/coverage-v8` 的 `generateReports` 里打一行日志，才看到 config 解析正常、但 project 内的 coverage 根本没进 provider。教训：**"配置不生效"要先确认配置有没有被读进去，再怀疑逻辑。**
3. **768–1023px 断点空洞。** 初版把底部导航的 `display: none` 写在 ≥768px，而左栏 / 右栏在 ≥1024px 才出现——中间这段宽度**导航整块消失**。桌面截图核对时发现。
4. **丹毒进度条填满。** `.bar > i` 少了 `width: var(--p)`，18% 显示成 100%。同样是截图核对时发现。这两条都说明：**外壳也要真的看一眼，结构化断言抓不到这类问题。**
5. **headless Chrome 的 `--window-size` 在 Windows 有最小宽度（约 500px）。** 390px 截图被裁切，看起来像横向溢出，实为窗口下限；改用 CDP `Emulation.setDeviceMetricsOverride` 才是真设备模拟（此时 `scrollWidth == innerWidth`，确认无溢出）。
6. **应用内浏览器截图不可用**（`visibilityState=hidden`，viewport 无可见表面）。最终采用「结构化验证（computed style / CSSOM / DOM 断言）+ headless CDP 截图」组合，两条路径都留下了证据。

#### 包体
